# 3. Общая архитектура

## 3.1. Принципиальная схема

```mermaid
graph TD
    subgraph Внешний мир
        A[Пользователь/Среда] -->|Сенсорные сигналы| B(Сенсорный препроцессор)
        F(Действия) --> A
    end

    subgraph Ядро агента
        B -->|События с важностью| C{Иерархическая рабочая память}

        subgraph "Управляющая система (Личность)"
            D[Система драйверов<br>5 потребностей] -->|События драйверов| C
            E[Эмоциональная система VAD] -->|Эмоциональный вектор| C
            C -->|Контекст + Эмоции| G[Наблюдатель (LLM)]
            G -->|Мысль (текст)| C
            C -->|Контекст + Мысль| H[Исполнитель (LLM)]
            H -->|Решение (действие/реплика)| C
        end

        C -->|Контекст для поиска| I[(Долговременная память<br>Эпизоды, Факты, Процедуры)]
        I -->|Воспоминания| C

        H -->|Запрос действия| J[Диспетчер действий]
        J -->|Команда| F

        H -->|Обновление весов| K[Механизм обучения<br>Привычки, Подкрепление]
        K -->|Изменение параметров| D
        K -->|Изменение параметров| E
        K -->|Новые процедуры| I

        L[MCP-интегратор] -->|Инструменты| J

        M[Мета-когнитивный модуль] -->|Мониторинг| C
        M -->|Инициация рефлексии| G
    end
```

## 3.2. Поток данных

1. **Сенсорный препроцессор** получает сырые сигналы из внешней среды (текст, события) и преобразует их в структурированные события с начальной важностью, тональностью, извлечёнными сущностями и эмбеддингом. Все операции выполняются детерминированно, без вызова LLM.

2. События попадают в **иерархическую рабочую память** с метками важности и времени.

3. **Драйверы** обновляют свои уровни (арифметически, по правилам) и при достижении порогов генерируют события.

4. **Эмоциональная система** обновляет вектор VAD на основе событий и правил.

5. **На каждом такте** (или по событию) запускается бикамеральный цикл:
   - Формируется контекст из рабочей памяти (Focus + Active + Background по важности)
   - **Наблюдатель** (LLM) генерирует мысль (текст)
   - Мысль добавляется в рабочую память
   - **Исполнитель** (LLM) генерирует решение: это может быть **внутренняя реплика** (продолжение диалога) или **внешнее действие**
   - Если решение — реплика, она добавляется в память, и цикл может повториться
   - Если решение — действие, оно передаётся диспетчеру

6. **Диспетчер действий** выполняет действие асинхронно, результат возвращается в память.

7. **Механизм обучения** анализирует результаты действий и обновляет параметры привычек.

8. **Мета-когнитивный модуль** отслеживает паттерны и инициирует рефлексию при необходимости.

## 3.3. Стратегии тиков (конфигурируемые)

| Стратегия | Описание | Когда использовать |
|-----------|----------|-------------------|
| **Фиксированные тики** | Цикл запускается каждые N мс (например, 100 мс) | Имитация непрерывного мышления, игры |
| **Событийный режим** | Цикл только при новых событиях важности > порога | Экономия ресурсов, чат-боты |
| **Гибридный режим** | Базовый тик (1 сек) + немедленный при важных событиях | Баланс непрерывности и экономии |

## 3.4. Глубина рефлексии (многошаговый внутренний диалог)

Для обеспечения полноценной рефлексии вводится понятие **глубины диалога**. Исполнитель может отвечать не только действием, но и внутренней репликой, помеченной как `[REFLECT]`. Такая реплика попадает в рабочую память и на следующем такте снова обрабатывается Наблюдателем, позволяя вести многошаговый диалог.

**Механизм:**
- В промпте Исполнителя явно указано, что он может генерировать либо действие, либо реплику (например, `[REFLECT] ...`)
- Система отслеживает счётчик итераций для текущего контекста (параметр `reflectionDepth`). При превышении лимита (конфигурируется) принудительно принимается решение действовать, чтобы избежать бесконечного цикла
- Мета-когнитивный модуль может анализировать глубину рефлексии и предлагать остановиться, если диалог становится бесплодным

**Пример многошагового диалога** см. в [Промпты](06-prompts.md).

## 3.5. Обработка прерываний (interruptibility)

**Механизм:**
- Каждое событие в системе имеет приоритет (0–10). События с приоритетом ≥ 8 считаются критическими (например, `cognitive_crisis`, `drive_event` с `urgency: 'high'`)
- При поступлении критического события во время выполнения многошагового диалога система:
  1. **Сохраняет контекст** текущего диалога: сериализует состояние рабочей памяти (фокус, активный контекст), текущую глубину рефлексии, значения драйверов и эмоций, указатель на последнюю мысль. Контекст помещается в **стек состояний** (с поддержкой вложенных прерываний, максимальная глубина стека конфигурируется)
  2. **Обрабатывает критическое событие** как новый, более приоритетный диалог (возможно, тоже многошаговый)
  3. После завершения обработки критического события система **восстанавливает контекст** из стека и продолжает прерванный диалог с того же места

**Пример:**
- Агент анализирует код (глубина рефлексии = 3)
- Поступает событие `drive_event` от драйвера безопасности с уровнем 0.9 (приоритет 9)
- Система сохраняет текущий стек мыслей, состояние драйверов и эмоций
- Запускается диалог обработки угрозы
- После завершения агент возвращается к анализу кода с фразой: «Продолжим анализ. На чём я остановился?»
